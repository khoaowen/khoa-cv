## Trigger options and recommendation for implementation lane

**Recommendation: use a narrowly scoped `workflow_run` handoff from the successful, trusted main CI workflow, rather than relying on the push event produced by an auto-merge.** This best addresses push suppression without adding a PAT or broadening the PR automation credential. Treat it as a candidate contract, subject to the artifact handoff from epic 1 and the implementation-time permission/security review; it is not a production change or final authorization.

- **Preferred candidate — `workflow_run` completion.** The trusted workflow must be identified by exact workflow, conclusion success, target branch `main`, and validated head SHA. Re-check that SHA is still an accepted main revision before deployment; obtain only an artifact produced by that exact workflow run and verify its run ID, branch, SHA, and digest. Use minimal read/artifact permissions in the consumer and keep deployment secrets inaccessible to PR/fork execution. Avoid checking out or executing untrusted PR code in the privileged consumer. Ensure a single well-defined validation/build artifact contract (ticket 1.2/epic 1 handoff); do not deploy an artifact built from a different revision.
- **Alternative — explicit `workflow_dispatch` after merge.** Could avoid dependence on push triggering, but requires an authenticated caller/credential and a safe SHA interface; a PAT is undesirable. Dispatch alone is not evidence of successful required checks, so the workflow must validate trusted main SHA and rerun the full release contract. Prefer only if existing automation can invoke it with a sufficiently narrow credential and tests prove provenance.
- **Alternative — `repository_dispatch`/external webhook.** Adds a caller credential and event-payload trust/replay surface. Not preferred absent an already-existing, narrowly scoped authenticated producer.
- **Alternative — replace GITHUB_TOKEN auto-merge credential.** A GitHub App or PAT may cause follow-on push workflows, but increases credential lifecycle and authorization burden and may violate the preference to avoid new broadly privileged credentials. Do not choose merely to restore push behavior.

### Contract tests and operational policy to carry into 2.2–2.7

- Trigger matrix: ordinary bot merge; Dependabot merge using `GITHUB_TOKEN`; explicit dispatch; failed/cancelled validation; irrelevant workflow completion; duplicate completion; out-of-order completion; current main advancing during a run.
- Trust gate: only a successful named upstream workflow for `main` and an exact, verified candidate SHA can proceed. PR/fork workflow code never receives deploy credentials. Failure or irrelevant completion cannot publish.
- Retry/idempotency: key attempts by source SHA plus validated artifact digest; retries for the same key are safe and observable. Record run/deployment identifiers and status.
- Supersession: immediately before deployment, compare candidate with current main. If superseded, do not publish it; record it as superseded by the later accepted SHA. Serialize deployments or guard the final publication step so a slow older completion cannot roll back newer main.
- Detection/notification: poll or schedule a check at a bounded interval (recommend **15 minutes** from successful qualifying main validation to deployed-SHA confirmation, with alert on breach). Notify a durable, actionable destination such as a dedicated GitHub issue/alert or repository Actions notification, including SHA/run links and recovery steps, never secrets or private contacts. Confirm destination ownership and delivery access in implementation planning.
- Success evidence: expose or retain a trustworthy link between main SHA, validation run/artifact digest, Cloudflare deployment identity, and served revision. A generic 200 response, CSS fingerprint, ETag, bot actor, or missing run alone is insufficient.
